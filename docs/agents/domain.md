# Доменная документация

Как инженерные навыки должны использовать доменную документацию репозитория при изучении кода.

## Перед изучением прочитайте

- **`GLOSSARY.md`** в корне репозитория или
- **`GLOSSARY-MAP.md`** в корне, если он существует: он указывает на отдельный `GLOSSARY.md` для каждого контекста. Прочитайте относящиеся к теме файлы.
- **`docs/adr/`**: прочитайте ADR, относящиеся к области изменений. В multi-context репозиториях также проверьте `src/<context>/docs/adr/`.

Если этих файлов нет, **продолжайте без предупреждений**. Не сообщайте об их отсутствии и не предлагайте создать их заранее. Навык `/domain-modeling` (вызываемый через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их по мере разрешения терминов и решений.

## Структура файлов

Single-context репозиторий (большинство репозиториев):

```text
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Multi-context репозиторий (при наличии `GLOSSARY-MAP.md` в корне):

```text
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← системные решения
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← решения контекста
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Используйте словарь глоссария

Когда результат называет доменное понятие (в заголовке задачи, предложении рефакторинга, гипотезе или имени теста), используйте термин из `GLOSSARY.md`. Не заменяйте его синонимами, которых глоссарий явно требует избегать.

Если нужного понятия в глоссарии нет, это сигнал: либо вы вводите термин, которого нет в проекте (пересмотрите формулировку), либо обнаружен реальный пробел (отметьте его для `/domain-modeling`).

## Отмечайте конфликты с ADR

Если результат противоречит существующему ADR, явно укажите это вместо негласного отклонения:

> _Противоречит ADR-0007 (event-sourced orders), но стоит пересмотреть, потому что…_
