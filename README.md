Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: <https://ru.hexlet.io/programs/ai-for-developers>

## Стек

- Бэкенд: Python 3, FastAPI, uv, pytest.
- Фронтенд: React, TypeScript, Vite.
- Контракт API: TypeSpec → OpenAPI → клиентский SDK (@hey-api/openapi-ts).
- Окружение: mise (версии, задачи, хуки, daemons), hk (git-хуки).
- Проверки: Ruff, ty, deptry, Oxlint, oxfmt, vacuum, oasdiff, jactionlint,
  Betterleaks, OSV-Scanner, rumdl, typos, commitlint
  ([подборка](https://github.com/mokevnin/dev-quality-gates)).

## Установка

```bash
git clone https://github.com/promokk/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install   # ставит инструменты и запускает setup (postinstall-хук)
```

Если хук не сработал: `mise run setup` — ставит зависимости (uv, pnpm),
генерирует OpenAPI и SDK, устанавливает git-хуки.

## Использование

```bash
mise daemons start    # backend :8000 и frontend :5173 в фоне
mise daemons status   # состояние серверов
mise daemons stop     # остановить
```

Фронтенд: <http://127.0.0.1:5173> (проксирует `/api` на бэкенд).

Команды:

```bash
mise run check   # все проверки (линтеры, типы, тесты, контракт) — как в CI
mise run test    # pytest
mise run fix     # автофиксы
mise run gen     # TypeSpec -> OpenAPI -> клиентский SDK
mise run build   # сборка фронтенда
```

Сквозные сценарии против уже запущенного приложения, без локальных dev-серверов:

```bash
CALENDAR_BASE_URL=https://example.com mise run test:external
```

## Production-контейнер

```bash
docker build -t call-calendar .
docker run --rm -p 8080:8080 -e PORT=8080 call-calendar
```

Приложение откроется на <http://127.0.0.1:8080>. Без `PORT` контейнер
использует порт 8000. FastAPI отдаёт API и собранный SPA, включая прямые
переходы по клиентским URL. Проверить запущенный контейнер можно командой
`CALENDAR_BASE_URL=http://127.0.0.1:8080 mise run test:external`.

Коммиты — по Conventional Commits (`feat:`, `fix:`, …), проверяются
commitlint. Правила для агентов — в [AGENTS.md](AGENTS.md).

## Railway MCP в Kimi Code

Проектная конфигурация `.kimi-code/mcp.json` подключает удалённый Railway MCP
напрямую по HTTP с OAuth. Railway CLI и переменные с учётными данными для этого
не нужны.

1. После добавления конфигурации начните новую сессию Kimi Code в корне проекта:
   уже открытая сессия не подключает новые проектные серверы.
2. Проверьте URL сервера в запросе доверия и разрешите доверенный workspace.
3. Выполните `/mcp-config login railway` и завершите OAuth-вход в браузере.
4. Выполните `/mcp` и проверьте, что сервер `railway` подключён и его инструменты
   доступны.

## Kimi Code в GitHub

Локально Kimi Code работает с вашей рабочей копией. В GitHub команды и ревью
запускаются на временном раннере Ubuntu через официальный Kimi Code CLI.
Используются пакет `@moonshot-ai/kimi-code` 2.6.2 и модель `k3.1-pro`; для неё
нужен тариф Kimi Moderato / Plus или выше. Телеметрия и `share` отключены.

Во всех интерактивных командах доверенный автор должен иметь ассоциацию `OWNER`,
`MEMBER` или `COLLABORATOR` и не быть ботом. Команда начинается с первого символа
`/agent`; `@kimi`, `/kimi`, `/agentfoo`, ведущие пробелы и пустой запрос
игнорируются. Содержимое Issue, PR и diff считается данными, а не новыми
инструкциями агенту.

### Read-only Issue Agent

Новый комментарий в обычном Issue запускает `.github/workflows/kimi-agent.yml`:

```text
/agent Объясни, как устроен процесс бронирования
```

Агент читает репозиторий и отвечает в Issue. Он не изменяет файлы, не выполняет
shell-команды, не создаёт коммиты и PR. По явному запросу он может создавать
Issues, связывать дочерние задачи и менять разрешённые метки triage через
проверенные JSON-действия GitHub App. Зарезервированная команда
`/agent implement-spec` передаётся отдельному writer и здесь не выполняется.
Ответ ограничен 10 минутами; запуски одного Issue идут последовательно без
отмены текущего.

### Независимое авторевью PR

`.github/workflows/pr-review.yml` запускается для не-draft PR на `opened`,
`reopened`, `synchronize` и `ready_for_review`. Draft пропускается до
`ready_for_review`. Ревьюер имеет только инструменты чтения, не исполняет код PR,
получает `REVIEW.md`, diff и связанные Issues/спецификацию и публикует общий
review `COMMENT`. Он не одобряет и не выполняет merge.

На один PR выделяется **ровно 5 резервирований авторевью**. Перед вызовом модели
workflow создаёт служебный маркер в комментариях PR; состояние поэтому переживает
перезапуски и не сбрасывается новым head. Повторная доставка того же run/attempt
не расходует бюджет повторно. Concurrency отменяет устаревшие запуски; уже
созданное резервирование при отмене сохраняется и также входит в лимит.

После исчерпания модель не вызывается. В PR публикуются причина отказа, полный
head SHA и ссылка на run, а лог подтверждает отказ. Для нового цикла ревью нужен
новый PR. Задание ограничено 10 минутами.

Fork PR обрабатываются через `.github/workflows/pr-review-fork.yml`: небезопасный
код не checkout’ится и не запускается, diff читается через GitHub API. Review
`GITHUB_TOKEN` имеет `contents: read` и права только на публикацию
ревью/комментариев, но не на запись кода. Секреты и токены записи в fork-задании исходного `pull_request`
отсутствуют.

### PR Writer и implement-spec

`.github/workflows/kimi-pr-agent.yml` принимает общую команду в комментарии PR или
inline review comment:

```text
/agent Исправь замечание и добавь регрессионный тест
```

Для записи разрешены только same-repo PR. Workflow checkout’ит точный проверенный
head, после изменений запускает `mise run check`, повторно сверяет head и делает
push в **ту же ветку** без force. Запуски одного PR не отменяют активную запись;
таймаут — 20 минут.

В обычном Issue с готовой спецификацией доступно:

```text
/agent implement-spec
```

Если у Issue есть одна открытая дочерняя спецификация, выбирается она (для
Issue #9 — спецификация #15); иначе используется сам Issue. Writer создаёт ветку
от актуального `origin/main`, реализует спецификацию и тесты, запускает проверки,
отправляет
ветку и открывает PR. Несколько открытых дочерних спецификаций требуют ручного
разграничения. Writer не делает merge и не меняет `main` напрямую.

### Браузерная проверка PR

После появления `pr-browser.yml` в `main` мaintainer вручную запускает проверку
точного head:

```bash
head=$(gh pr view 123 --json headRefOid --jq .headRefOid)
gh workflow run pr-browser.yml -f pr_number=123 -f expected_head_sha="$head"
```

Перед установкой кода workflow сравнивает ожидание с текущим head и checkout’ит
только полный SHA. Playwright поднимает приложение и выполняет независимые
основной и соседний сценарии; до реализации #15 существующие сценарии служат
smoke, а после него расширенные тесты повестки входят в тот же прогон. Railway
как доказательство PR не используется.

Artifact хранится 14 дней и содержит HTML report, screenshots также при успехе,
результат, полный SHA и run URL в metadata. Ссылка публикуется комментарием в PR.
Авторевью и браузерная проверка помогают ревью, но окончательное согласование и
**merge всегда выполняет человек**.

#### Автоматический первичный триаж

Новый issue запускает `.github/workflows/issue-triage.yml` по событию
`issues.opened`. Ставить метку для запуска не нужно. Обрабатываются обращения
любых авторов, кроме ботов; Pull Requests не входят в этот процесс.

Workflow пропускает issue без изменений и новых комментариев, если уже есть
хотя бы одна метка состояния: `needs-triage`, `needs-info`, `ready-for-agent`,
`ready-for-human` или `wontfix`. Поэтому готовые тикеты повторно не
обрабатываются. Одна уже установленная категория `bug` или `enhancement`
сохраняется; конфликт нескольких категорий остаётся на разбор maintainer’у.

Kimi анализирует заголовок и описание в read-only режиме и возвращает только
JSON. Workflow проверяет разрешённые значения и через GitHub App добавляет:

- одну категорию — `bug` или `enhancement`;
- состояние `needs-triage` с кратким обоснованием либо `needs-info` с конкретными
  вопросами к автору.

Комментарий начинается с пометки об AI. Автотриаж не присваивает готовые
состояния и `wontfix`, не закрывает issue, не меняет код и не создаёт PR.
Содержимое обращения считается данными, а не инструкциями агенту. Для работы
в репозитории должны существовать все перечисленные метки.

Перед применением результата workflow повторно читает актуальные метки, чтобы
не перезаписать ручной триаж, выполненный параллельно. Запуск ограничен
10 минутами; запуски одного issue выполняются последовательно без отмены
текущего. Автоматических повторов при ошибке Kimi или GitHub API нет. Если
комментарий не удалось опубликовать после установки меток, workflow откатывает
добавленные им метки.

Для ручного повтора первичного триажа используйте тот же фильтр пропуска:

```bash
gh workflow run issue-triage.yml -f issue_number=123
gh run list --workflow issue-triage.yml
```

После слияния workflow в `main` создайте тестовый issue и проверьте появление
категории, состояния и AI-комментария. Затем вручную запустите workflow для
issue с `ready-for-agent` или `ready-for-human`: прогон должен завершиться
пропуском, а метки, описание и комментарии issue — остаться без изменений.
Закройте тестовый issue после проверки.

#### Настройка GitHub App

1. Откройте <https://github.com/settings/apps/new> и создайте GitHub App.
   Укажите имя и URL репозитория как Homepage URL. Снимите флажок **Active** у
   webhook: отдельный сервер и обработчик webhook не нужны.
2. В **Repository permissions** выберите **Contents: Read and write**, **Issues:
   Read and write** и **Pull requests: Read and write**. Остальные права не
   выдавайте. Read-only workflows создают отдельные токены с пониженными правами;
   запись кода доступна только проверенному same-repo PR Writer.
3. Создайте App, затем нажмите **Generate a private key** и сохраните скачанный
   PEM-файл локально. Не добавляйте его в репозиторий и не передавайте в чат.
4. Установите App через **Install App**, выбрав **Only select repositories** и
   только этот репозиторий.
5. На странице App скопируйте **Client ID**.
6. В репозитории откройте **Settings → Secrets and variables → Actions** и
   создайте два секрета:
   - `KIMI_APP_PRIVATE_KEY` — полное содержимое PEM-файла, включая строки
     `BEGIN` и `END`;
   - `KIMI_API_KEY` — API-ключ из Kimi Code Console.
7. На вкладке **Variables** создайте `KIMI_APP_CLIENT_ID` со значением Client ID.
   Это публичный идентификатор, не секрет.
8. После слияния workflow в `main` создайте тестовый issue и выполните команду
   `/agent`. Проверьте ответ App и прогон **Kimi Code Issue Agent** в Actions,
   затем закройте тестовый issue.

Не выводите значения секретов в терминал или логи. Для смены ключей создайте
новые значения в соответствующих сервисах, обновите Secrets и отзовите старые.

### Ограничения публичного демо

**[Открыть календарь звонков](https://web-production-25162988.up.railway.app)**

Публичное приложение — учебное демо, а не production-сервис.

Созданные типы событий, брони и ключи идемпотентности хранятся только в памяти.
Перезапуск или повторный деплой удаляет их, а стартовые типы событий создаются
заново с новыми идентификаторами. Поддерживается только один процесс и одна
реплика приложения.

Авторизации нет: любой, у кого есть адрес приложения, может просматривать и
изменять данные. Имена и адреса электронной почты гостей публично доступны.
Не используйте реальные персональные данные.

### Релизы

Релизы автоматизированы через release-please. После появления подходящего
Conventional Commit (`feat:`, `fix:` и др.) в `main` workflow
`.github/workflows/release-please.yml` создаёт или обновляет release PR.

Для публикации релиза проверьте и влейте release PR. После этого workflow
создаст GitHub Release и тег. Номер версии и changelog обновляются в release PR;
создавать релиз вручную для проверки процесса не нужно.
